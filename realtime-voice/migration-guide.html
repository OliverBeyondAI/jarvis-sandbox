Architecture Change

Integration Points & Changes Required

Each integration point requires specific changes. Critical items affect call flow directly; major items change existing APIs; minor items are configuration-only.

Critical Twilio Call Routing

Replace ConversationRelay TwiML with SIP trunk configuration pointing to OpenAI's SIP endpoint.

  • Remove ConversationRelay WebSocket handler
  • Remove TwiML <Connect><ConversationRelay> verb
  • Add Twilio SIP Trunk to OpenAI SIP endpoint
  • Add Session creation webhook for inbound calls
  • Modify Twilio phone number routing to SIP trunk

Critical Audio Pipeline

Eliminate the STT → LLM → TTS orchestration chain. The Realtime API handles this internally.

  • Remove ElevenLabs TTS client and streaming logic
  • Remove STT integration (Whisper/Deepgram/etc.)
  • Remove Audio format conversion / transcoding
  • Add G.711 ulaw format config on session create
  • Remove Audio chunk buffering / assembly

Critical LLM Integration

Replace Claude/Bedrock REST calls with OpenAI Realtime WebSocket event protocol.

  • Remove Bedrock client and Claude API calls
  • Add OpenAI Realtime WebSocket connection mgmt
  • Modify System prompt format (minor syntax changes)
  • Modify Tool schemas (Claude → OpenAI format)
  • Add Event-driven response handling

Major Session Management

Shift from managing conversation context in your app to the API's server-side state model.

  • Modify Session lifecycle (create via REST, use via WS)
  • Add Ephemeral token generation for security
  • Modify Context management (use conversation.item events)
  • Add Session config (voice, VAD, temp, max_tokens)

Major Voice & Persona

Replace ElevenLabs voice selection with GPT Realtime's 8 built-in voices. Voice cloning is not available.

  • Remove ElevenLabs voice_id configuration
  • Remove Custom voice cloning / fine-tuning
  • Add Voice selection from 8 built-in options
  • Modify Voice personality via system instructions

Minor Monitoring & Logging

Adapt observability from multi-service traces to single-connection event logging.

  • Modify Latency measurement (single hop now)
  • Add OpenAI tracing config (workflow_name, group_id)
  • Remove Cross-service correlation IDs
  • Modify Cost tracking (token-based, not per-minute)

Migration Plan

A phased approach that allows incremental validation before cutting over production traffic. Each phase is independently testable and reversible.

Phase 1 — Foundation

OpenAI Realtime API Integration

Stand up the core Realtime API connection and validate basic text+audio round-trips before touching telephony.

  • Create OpenAI project and provision API keys with Realtime API access
  • Implement WebSocket connection manager using the OpenAI Python SDK (client.realtime.connect())
  • Port system prompts and personality instructions to the new session config format
  • Convert tool/function schemas from Claude's format to OpenAI's function-calling schema
  • Build event handler for the full event lifecycle: session.created, response.audio.delta, response.done, error
  • Validate with the browser-based prototype (see realtime-voice/) before proceeding
session_manager.py — Core session creation
from openai import AsyncOpenAI client = AsyncOpenAI() async def create_voice_session(voice="ash", model="gpt-4o-mini-realtime-preview"): """Create a Realtime API session optimized for telephony.""" session = await client.beta.realtime.sessions.create( model=model, voice=voice, modalities=["text", "audio"], instructions=SYSTEM_PROMPT, input_audio_format="g711_ulaw", # Native telephony codec output_audio_format="g711_ulaw", turn_detection={ "type": "semantic_vad", "eagerness": "high", }, temperature=0.6, max_response_output_tokens=512, ) return session
Phase 2 — SIP Telephony

Twilio SIP Trunk Configuration

Replace ConversationRelay with SIP trunking to route PSTN calls directly to the Realtime API.

  • Create a Twilio Elastic SIP Trunk in the Twilio console
  • Configure the Origination URI to point to OpenAI's SIP endpoint
  • Set up a webhook endpoint on your server that Twilio calls on inbound INVITE — this creates the Realtime session and returns SIP routing info
  • Update the Twilio phone number to route to the SIP trunk instead of a TwiML app
  • Configure G.711 u-law as the audio codec (no transcoding needed)
  • Test with a staging phone number before touching production numbers
SIP INVITE flow: Twilio receives inbound PSTN call → sends SIP INVITE to OpenAI's SIP endpoint → OpenAI connects the call audio to a Realtime API session. Your server handles session config via a webhook, not the audio stream itself.
sip_webhook.py — Inbound call handler
async def handle_inbound_call(request): """Webhook called by Twilio on inbound SIP INVITE. Creates a Realtime session and returns connection config.""" caller = request.json.get("From") # Create session with caller-specific context session = await create_voice_session( voice="ash", model="gpt-4o-mini-realtime-preview", ) # Return session token for SIP bridge return { "session_id": session.id, "token": session.client_secret.value, "model": "gpt-4o-mini-realtime-preview", }
Phase 3 — Decommission Legacy

Remove ElevenLabs, Bedrock, and ConversationRelay

After validating the new stack with live traffic, remove the legacy integration code and vendor dependencies.

  • Remove ElevenLabs SDK dependency, API key, and TTS streaming code
  • Remove AWS Bedrock Claude client and associated IAM permissions
  • Remove Twilio ConversationRelay WebSocket handler and TwiML generation
  • Remove audio transcoding utilities (format conversion, resampling)
  • Remove STT integration code (Whisper/Deepgram/etc.)
  • Update environment variables: remove ELEVENLABS_API_KEY, AWS_* Bedrock vars
  • Remove unused Python packages: boto3, elevenlabs, anthropic (if Bedrock-only)
Keep the legacy stack available behind a feature flag for at least 2 weeks after cutover. If GPT Realtime has an outage or quality regression, you need a fast rollback path.
Phase 4 — Optimization

Tune, Monitor, and Extend

Once stable on the new stack, optimize latency, cost, and quality using Realtime-specific features.

  • Tune semantic VAD eagerness per use case (high for quick Q&A, low for dictation)
  • Enable input audio noise reduction for noisy call environments
  • Implement max_response_output_tokens caps to control cost and response length
  • Set up OpenAI tracing with workflow_name and group_id for call analytics
  • Evaluate gpt-4o-mini-realtime vs gpt-4o-realtime for cost/quality trade-offs
  • Build cost dashboards based on token usage (audio tokens ~32-50 per second)
  • Consider cached audio input tokens (50% discount) for repeated greetings/prompts

Risks & Mitigations

High
Voice Quality Regression

GPT Realtime's 8 built-in voices may not match the quality, variety, or brand-specific tuning achievable with ElevenLabs voice cloning.

Mitigation: Conduct blind A/B listening tests before migration. If a specific voice is brand-critical, consider keeping ElevenLabs for that use case while migrating the rest.
High
LLM Quality Differences

GPT-4o Realtime may produce different quality responses than Claude for your specific use cases. Tool-calling behavior, instruction following, and safety filters differ between models.

Mitigation: Run parallel evaluation on a test suite of real conversation transcripts. Compare response quality, tool-call accuracy, and edge-case handling before cutover.
Medium
Single Vendor Lock-in

Moving from a multi-vendor stack to all-OpenAI creates a single point of failure. An OpenAI outage would take down the entire voice pipeline.

Mitigation: Keep the legacy stack deployable behind a feature flag for fast failover. Monitor OpenAI status page and set up automated fallback triggers.
Medium
SIP Configuration Complexity

SIP trunking is a lower-level telephony primitive than ConversationRelay. Misconfiguration can cause silent failures, one-way audio, or codec mismatches.

Mitigation: Test on staging numbers first. Validate bidirectional audio with G.711 u-law. Set up monitoring for SIP error codes (4xx, 5xx) and RTP packet loss.
Medium
WebSocket Connection Stability

Long-running phone calls rely on a persistent WebSocket to OpenAI. Network issues or API-side disconnects mid-call would drop the conversation.

Mitigation: Implement automatic reconnection with exponential backoff. Use conversation.item.create to restore context on reconnect. Set up heartbeat/ping monitoring.
Low
Cost Unpredictability

Token-based pricing (vs. per-minute) makes costs harder to predict, especially for long or chatty conversations.

Mitigation: Set max_response_output_tokens to cap response length. Monitor token usage per call. Use gpt-4o-mini-realtime for cost-sensitive paths.

Pre-Migration Checklist

Before Starting

  • OpenAI API key with Realtime API access provisioned
  • Twilio account with Elastic SIP Trunking enabled
  • Staging phone number allocated for testing
  • Voice A/B test results reviewed and approved
  • Tool/function schemas ported from Claude to OpenAI format
  • System prompts adapted for GPT-4o behavior
  • Cost projections validated against real token usage

Before Go-Live

  • End-to-end call test on staging (PSTN → SIP → Realtime)
  • Latency measured and within target (<500ms first audio)
  • Tool calling validated for all critical functions
  • Fallback to legacy stack tested and documented
  • Monitoring dashboards configured (latency, errors, cost)
  • On-call runbook updated with new architecture
  • Legacy vendor contracts reviewed for cancellation terms

Key Code Transformations

Side-by-side examples showing the most important code changes when migrating from the current stack to GPT Realtime.

Tool / Function Schema

Claude / Bedrock (before)
{ "name": "lookup_order", "description": "Look up order status", "input_schema": { "type": "object", "properties": { "order_id": { "type": "string" } }, "required": ["order_id"] } }
OpenAI Realtime (after)
{ "type": "function", "name": "lookup_order", "description": "Look up order status", "parameters": { "type": "object", "properties": { "order_id": { "type": "string" } }, "required": ["order_id"] } }

Handling a Tool Call Response

Claude / Bedrock (before)
# Receive tool_use block in response tool_use = response["content"][0] result = execute_tool( tool_use["name"], tool_use["input"] ) # Send tool_result back messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": tool_use["id"], "content": json.dumps(result) }] })
OpenAI Realtime (after)
# Receive function_call event if event.type == "response.function_call_arguments.done": result = execute_tool( event.name, json.loads(event.arguments) ) # Send function output via WebSocket await conn.conversation.item.create(item={ "type": "function_call_output", "call_id": event.call_id, "output": json.dumps(result) }) await conn.response.create()
Key difference: Claude uses input_schema for tool definitions; OpenAI uses parameters. Claude returns tool_use content blocks; OpenAI emits response.function_call_arguments.done events. The JSON schema for parameters is identical — only the wrapper changes.
